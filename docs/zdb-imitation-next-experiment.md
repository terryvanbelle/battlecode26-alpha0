# Proposed next experiment: zdb imitation followed by RL

Status: design draft, no teacher collection or training launched. This follows the user's November 11 proposal to pretrain on vibe26b_zdb moves before switching to RL. It changes the earlier prohibition on using this opponent as a teacher for this new lineage only; all historical experiments and their exclusions remain unchanged.

Hypothesis: learning the expert's state-dependent behavior across full games, including the feature encoder, supplies a better starting policy than further fitting a small output head on sparse root labels. Improved supervised accuracy alone does not establish playing strength.

First resolve action compatibility. The current macro_v2 policy selects one of 40 complete-turn macros whose navigation, targeting and primitive ordering are fixed heuristics. zdb produces its own primitive controller calls. Logging a move direction and assigning the nearest macro would silently change the teaching objective. Build a versioned recorder for legal observations and ordered legal controller calls, including action arguments, robot/team/turn identity and any required history. Measure whether current macros can reproduce those decisions on the same state, with explicit unmatched and ambiguous counts. Do not prune difficult positions or label an approximation as exact imitation. If coverage is inadequate, preregister a primitive-action or richer action interface before training; that becomes a separate model/runtime lineage.

Collect new teacher games using preregistered source maps, opponents and seeds. Preserve the original ancestry-excluded maps. Never ingest existing development/confirmation trajectories. Split by entire source game and seed, not individual turns, and retain all outcomes. Cap and balance contributions by game and role so long games do not dominate. Freeze complete data manifests and train/validation exclusions before gradients. Teacher code supplies behavior, never a deployed runtime dependency.

Train the encoder and policy on teacher actions, not only the 5,160-parameter output head. If the action/observation interface changes, use a new model version rather than reinterpret cp2 weights. Evaluate held-out action prediction, legal-action coverage and full-game imitation-only play. Predeclare model size, update budgets, optimizer, data schedule and checkpoint selection before seeing evaluation outcomes.

Then fine-tune with fresh self-play RL and a fixed training league. Keep a frozen imitation-only checkpoint and a matched RL-only control with the same architecture, environment and RL interaction budget. Preregister any retention loss or mixture schedule rather than tune it on development outcomes. The central comparison is imitation-plus-RL versus RL-only; imitation-only reveals whether RL preserves or improves the starting policy.

Evaluation disclosure: development-v4 remains the unchanged historical regression panel and is still reported in full, including zdb. For this new lineage zdb is an exposed teacher, so its score is not evidence of generalization to an unseen opponent. Do not change the existing panel, thresholds, original baseline or historical claims. Preregister an additional independent opponent panel with unused evaluation seeds before teacher training, excluding teacher-derived or otherwise exposed opponents, to assess transfer. Fresh confirmation outcomes remain excluded from training and tuning. No automatic promotion or tournament submission.

Before launch: review the current V11 deadline interruption and preserve its completed benchmark evidence; complete the action-compatibility feasibility review; freeze the complete new collection/training/RL/evaluation protocol and test its isolation, provenance, locks, watchdogs and recovery. No paid infrastructure or GCloud use. Deployable execution must use legal observations and standard APIs entirely in Java within official limits.

## Static feasibility review — November 11

The reproducible inventory in `diagnostics/zdb-imitation-planning/static-interface-inventory.json` pins the teacher, macro implementation and current model/features. It scans Java controller call sites after suppressing comments and strings; it is not a runtime frequency or reachability measurement. Teacher source has two `readSharedArray`, one `writeSharedArray`, seven `readSqueaks` and twelve `squeak` call sites. MacroV2 has none of these calls. `Sym.java` retains a map-sized `mem` array and symmetry state across turns. `RobotPlayer.java` runs background flow work and branches on bytecode budget. `network_v2.py` is feed-forward and has no carried recurrent state.

Consequently, exact imitation of arbitrary full teacher controller traces is outside the current macro interface. The empirical unmatched-turn fraction is still unknown. An imitation failure under this interface would confound model capacity with unavailable actions and missing historical information. Do not collapse communication into hold, invent macro labels, or copy teacher private memory into observations.

Selected implementation direction for the feasibility prototype: a separately versioned legal-observation student with ordered primitive decisions and per-robot recurrent state. Predict a primitive operation, its typed arguments and an end-turn token; refresh legal masks and observations after each executed primitive. Legal operation vocabulary must include the applicable communication actions. Encode shared-array/message observations through standard APIs. Maintain recurrent state by robot identity, reset at game start and robot creation, and never leak opponent memory or engine-private state. The precise observation schema, memory size and architecture are not frozen yet. Preserve cp2 and all macro_v2 checkpoints as a different model/interface lineage; no weight reinterpretation.

Recorder requirements before any teacher dataset:

1. Record only legal, student-available observations, ordered primitive calls/arguments, success/failure and turn boundaries. Include information needed to distinguish role, robot identity, round, facing, cooldown and received communication. Teacher internal globals are audit-only if inspected, never student features.
2. Keep collection in separate storage, source manifests, locks and seed namespace. Preserve all source outcomes; split by complete games. No existing benchmark or confirmation replay is a demonstration.
3. Capture calls outside the teacher's charged bytecode path where possible. zdb uses clock-budget-sensitive work; a wrapper that changes its budget can change the teacher itself. Require paired instrumented/uninstrumented deterministic trace and terminal-equivalence checks under the same official execution limits before accepting labels. A failure stops collection for instrumentation review.
4. Verify serialization, argument legality, observation availability and exact primitive replay. Verify all scheduled games, including errors and unmatched turns; do not prune. Quantitative dynamic expressibility claims require complete preregistered traces.
5. Freeze unused source/validation/evaluation seeds, independent opponent panel and numerical imitation competence criteria before supervised outcomes. Test training-fit capacity separately from held-out prediction and full-game performance. Only competent imitation-only play opens the RL phase.

No teacher games, action labels, gradients or new RL experiment were produced by this static review. Current official tournament limits still need independent verification before claiming tournament compatibility; values written in teacher comments are not authoritative rules.
